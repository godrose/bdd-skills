# Discovery: `/bdd:deliver`, one conversation from description to verified

Input: issue #41 ("Make discovery, implementation, and verification one conversation"), a read of the existing commands, and a discovery dialogue with the builder on 2026-11-09.

## Story

A product manager, with a developer or architect watching, describes a change in plain language. The plugin asks one focused question at a time until the examples are agreed. It then writes the scenarios, implements them and verifies them, and reports each agreed example as passed, failed or couldn't be checked, with a line on what the change did to the older scenarios of the same feature.

After the first implementation the team speaks one language. Each later change starts as a description and adds visible value on top of what exists.

## Existing behavior (from the commands)

- `discover` asks questions one at a time and ends in a pack that says "ready for `bdd:design`". Step 3b already looks for existing behavior in the code and the feature files.
- `design` runs in `specify-and-implement` mode by default: design, approval, implement through the implementer role, verify. It writes no `.feature` file before approval.
- `implement` has a fix loop with a cap ("Max retries per step: 3") and stops and reports when a reused `Then` does not fit the scenario's data. It has a red-first check that can leave a scenario unautomated, with "not seen red".
- `run` never counts a run of zero tests as a pass.
- Commands call each other through the Skill Roles table, for example "invoke the implementer skill".
- The marketplace plugin pre-approves no tools and ships no decision log script, so there a decision log records nothing.
- A project install writes each command's former `allowed-tools` back, from a table in `install.sh`.

## What the issue asks, and the verdict

| Ask | Verdict |
|-----|---------|
| One entry point that carries agreed examples through the existing workflow | This pack. Composition, not a rewrite. |
| Ask one question when a decision is open, record it, continue without asking approval again | Yes, with two light gates (decision 4). |
| Fix the implementation or the test and rerun | Reuse `implement`'s loop. Never change an approved scenario or its expected values. |
| Report each example as passed, failed or couldn't be checked | Yes (decision 8). |
| `.first()` guidance | Done in #42. |
| Empty `Given <prerequisite> exists` | Separate. It reverses a choice in `design.md` and needs its own question. Not part of this pack. |

## Existing users

- **Marketplace and project installs:** nothing changes until `0.7.0`. After it, `/bdd:deliver` exists and no existing command changes what it does when you do not use it. Their added hooks apply only when `deliver` calls them.
- **`bdd-config.md`:** nothing is rewritten. `install.sh` prints a note for the new row if the config lacks it, as it does for other newer rows.
- **A user's own files:** a project that already has a `docs/out-of-scope.md` of its own keeps it. `deliver` reads it, and adds entries in the same one-line format. It never rewrites existing lines.
- **A user's own file named `bdd-deliver.md`:** `install.sh` today overwrites any `bdd-<name>.md` at the target without checking whose it is. That is how updates work, but for a new name it can replace a user's own command. Decision 16: `install.sh` skips a `bdd-deliver.md` that lacks the installer's `# Source:` line, and says so. The plugin form has no such problem, because plugin commands are namespaced (`/bdd:deliver`).

## First run

In a project with no config, `deliver` says to run `/bdd:init`, as the other commands do. In a project with config but no feature files, `discover`'s step 3b reports "nothing to mine" and the flow goes on. Without an out-of-scope file it creates one when the first entry is written. Nothing is created before the PM has approved something.

## Edge and negative cases

1. The description matches existing behavior: scenarios for existing behavior, marked "from code", and the report says it already works.
2. The description contradicts an out-of-scope entry: one question to the PM whether to reverse it. A reversal is recorded as a dated line, and the old entry is left in place.
3. An older scenario fails after the change: asked as a changed-behavior decision (decision 7).
4. A reused `Then` does not fit the data: a product decision, asked at once.
5. A step fails three times: parked (decision 7).
6. A run executes zero tests: not a pass, and the report says so.
7. A scenario was not seen red: reported "couldn't be checked", with the reason.
8. The decision log is on and the script is missing: "Nothing was recorded" for the log. The answers are still in the feature description.
9. A tracker key with no requirements-sync skill: ask for the text, as `discover` does.
10. A feature file was deleted outside the flow: found through the local git search. A shallow clone has no history, and `deliver` says it cannot look.
11. The session ends before the examples are approved: nothing is written.
12. `workflow_mode` is `specify-only`: `deliver` stops after the go-ahead and says the scenarios are specified and not implemented.
13. The out-of-scope file exists but is not in the one-line format: read it as plain text, add entries in the format, and rewrite nothing.

## Exclusions

1. No visual tool and no whole-suite mode. The report has a fixed shape so a tool could read it later.
2. No change to the approval rules beyond the two gates in decision 4.
3. No write-back to the tracker and no automatic pull request.
4. No new script, hook or MCP server.
5. No change to the empty-`Given` guidance. It is a separate question.
6. No resume file.
7. No attempt to make the flow work for a PM with no developer. The plugin pre-approves nothing, so shell and file calls prompt, and someone must answer them.

## Tests to write first

Each must fail before the change.

- `plugin/commands/deliver.md` exists, has a description, and carries no `allowed-tools`.
- It names the four steps in order and the two gates, and says no `.feature` file is written before the go-ahead.
- It says a product decision is asked at once and a technical stop is parked.
- It never lets the agent change an approved scenario or its expected values.
- The report shape names passed, failed, couldn't be checked, a regression line and a developer note.
- `discover.md` reads the out-of-scope list and ends with the checklist shape. `design.md` accepts the checklist and writes answers into the feature description. `implement.md` has the open-decision shape.
- The template has the `out_of_scope_file` row, and `install.sh` prints a note when a config lacks it.
- The project install writes `bdd-deliver` with the grant union. The plugin copy has no grants. A `bdd-deliver.md` without the installer's source line is left alone.
- The README, the file tree, the docs index and the changelog name the command.

## Trial after the change

Run it by hand on a small project: one description, one open question, one old scenario that changes. Record what it asked and what the report said. Run the eval case. Then submit the new version.

## Amendment (2026-11-09): look at the result

Two trials on a real project (a .NET project with two test suites, see the description of the pull request that added `deliver`) showed that passing scenarios can describe something that never happens. Two examples about a Starting and a Running experiment passed for a whole day while the screen showed Draft. The data file declared those statuses, and the sync service reverted them at once because no job stood behind them. The scenarios checked only the time, and no one looked at the page. An unused "Started" row on the details page also went unseen, because no scenario can fail on a leftover label.

| # | Question | Decision | Reason |
|---|----------|----------|--------|
| 17 | Does `deliver` look at the result before it reports? | Yes. A new step 5 comes after the run and before the report. | A green run proves the scenarios can fail. It does not prove they describe what a person sees. |
| 18 | How is the result looked at? | By the means the layer offers. A screen: open the app on the scenarios' data, or take a screenshot during a run, and read it. No screen: make a real request, read the stored record, or read the log or record a job writes. | The builder asked for the screen check for end-to-end examples and a matching technique for work with no screen. |
| 19 | What is compared? | The agreed examples, and for a screen also anything the page shows that no scenario names. Every state that a scenario's data declares is checked again once the system runs. | The two defects were an unnamed leftover and a declared state the system changed. |
| 20 | What if the result cannot be looked at? | Say what was not looked at and why. Never report passed for an example whose result could be looked at and was not. | A skipped check must not look like a passed one. |
| 21 | What does the report say? | A `Seen:` line after the regression line. A surprise that was fixed still goes in the developer note. | The reader sees what was observed, not only what was run. |

Tests written first: `tests/test_deliver.sh` section 19 fails before the change. It adds a step and changes no earlier decision. No eval is added: `deliver-first-gate` stops at the first question.

Known limit: the command text names the techniques but cannot start an app by itself. In a project with no way to start the app from the session, the step ends in "not looked at", which is allowed and visible.
